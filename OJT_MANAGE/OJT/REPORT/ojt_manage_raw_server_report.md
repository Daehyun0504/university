## 1. 프로젝트 목적 및 접근 방식

본 프로젝트는 「프로젝트 관리 실무」 교육에서 네트워크 서버 개발을 실습 주제로 선정한 것이다. 교육의 목적은 하나의 결과물을 만드는 과정에서 목표·범위 설정, 작업 분해, 수행·검증, 진척·위험 통제와 변경·종료 관리를 익히는 데 있다.

기술 목표는 프레임워크 없이 요청 수신·해석·응답을 직접 구현하여 네트워크를 깊이 이해하는 것이다. 따라서 결과는 서버의 동작과 함께 무엇을 만들기로 했는지, 작업과 위험을 어떻게 나누었는지, 완료 여부를 어떤 증거로 판단했는지를 함께 설명한다.

구현 언어는 Python이며 표준 라이브러리의 `socket`을 사용한다. Flask·Django·FastAPI 같은 웹 프레임워크와 완성된 HTTP 서버 기능인 `http.server`를 사용하지 않고, 연결 수락, 요청 파싱, 파일 처리와 응답 조립을 프로젝트 코드에서 수행한다. 실행 의존 패키지는 없으며 pytest는 자동 시험에 사용한다.

여기서 Raw_Server는 TCP 소켓 API 위에 HTTP 처리 로직을 직접 구현했다는 의미다. 사용 소켓은 IPv4의 `SOCK_STREAM`이며, IP 패킷을 직접 만드는 `SOCK_RAW` 서버를 뜻하지 않는다. TCP 연결 수립·재전송·순서 보장 등은 운영체제의 TCP/IP 기능을 사용하고, 프로그램은 전달받은 바이트의 의미와 요청 처리 정책을 담당한다.

본 보고서는 가상 수행 사례가 아니라 현재 소스와 계획 문서, 이번 자동 시험 결과를 근거로 작성하였다. 코드 구현, 로컬 검증, 실제 다른 기기 검증의 상태를 구분한다.

## 2. 프로젝트 관리 적용 및 수행 기록

### 2.1 계획을 관리 가능한 작업으로 구체화

[15주 교육 계획](./ojt_manage_plan.md)은 1~3주차 계획 수립, 4~7주차 수행, 8~11주차 통제, 12~15주차 변경 관리·종료로 구성되어 있다. 이를 [통합 계획 문서](./docs/ojt_manage_planning.md)에 요구사항, WBS, 위험, 시험 결과와 변경 양식으로 구체화하였다. 주차는 교육 계획이며 실제 수업이 해당 시점까지 완료되었다는 의미는 아니다.

| 관리 영역 | 이 프로젝트에 적용한 방법 | 확인 기록 및 현재 상태 |
| --- | --- | --- |
| 목표·범위 | 정적 GET·IPv4·순차 처리를 필수 범위로 정하고 확장 기능 구분 | REQ-001~012와 완료 기준 작성 |
| 작업·일정 | Echo → 요청 파서 → 응답·파일 → 연결·검증으로 작업과 선후 관계 분해 | WBS-001~011 및 주차 계획 작성, 실제 일정 평가 대기 |
| 수행·품질 | 기능별 모듈 구현, 단위·소켓 통합 시험으로 완료 증거 연결 | src와 tests 구현, 이번 자동 시험 77개 통과 |
| 위험·이슈 | 분할 수신·느린 입력·경로 탈출·환경 차이에 대응책 마련 | 위험표, 제한 처리와 관련 시험, 환경 문제 해결 기록 |
| 변경·기록 | 실행 안내·스크립트 보완, 추가 기능의 영향 분석·결정 양식 준비 | 실행 파일·문서 반영, 추가 서버 기능의 별도 승인 변경 없음 |
| 진척·종료 | 코드 준비·자동 검증과 실제 기기·수업 승인 상태를 구분 | LAN·스마트폰·최종 발표·종료는 대기 |

요구사항은 시험 가능한 기준으로 표현하였다. 예를 들어 REQ-003은 GET /에 한글 HTML과 200을 반환하는 것으로 정하고, handler.py 및 실제 HTTP 접속 시험과 연결하였다. REQ-010은 LAN 수신 옵션 구현과 실제 기기 접속을 구분하여, 옵션이 있다는 이유만으로 완료 처리하지 않았다.

### 2.2 수행 결과와 위험을 점검한 방법

전체 작업을 단순한 서버 완성 여부로 판단하지 않고 요청 파서, 응답 생성, 파일 처리, 연결 종료 등으로 나누어 구현과 시험을 연결하였다. 단위 시험으로 내부 처리 결과를 확인하고 소켓 통합 시험으로 실제 연결·응답·복구를 점검하였다. 이번 보고 작성 시에도 기존 시험을 재실행하여 현재 코드의 상태를 확인하였다.

기술 위험은 대응 코드와 시험으로 연결하였다. TCP 수신 경계를 잘못 가정할 위험에는 헤더 누적과 분할 수신 시험을, 느린 입력에는 전체 수신 시간 제한을, 경로 탈출에는 문서 루트 검사와 외부 심볼릭 링크 시험을 적용하였다. 실제 LAN 환경 차이는 아직 검증하지 않은 위험으로 남겼다.

기존 문서에는 가상환경 생성 중 ensurepip 부재를 해결하고 설치·시험 환경을 준비한 기록이 있다. 압축 파일의 MIME 처리 보완과 회귀시험도 기록되어 있다. 이처럼 문제의 증상, 대응과 재확인 결과를 함께 남겼으며, 기존 기록과 이번 재검증 결과를 구분하였다.

### 2.3 변경과 미완료 항목을 관리한 방법

이번 작업 과정에서는 사용자 요청에 따라 서버·클라이언트 실행 스크립트를 만들고 안내 문서를 보완하였다. 서버 기능 확대와 실행 편의 보완을 구분하고, 관련 파일 및 사용법을 함께 갱신하였다. 동시 처리·Keep-Alive 등 추가 기능은 현재 범위에 포함하지 않고 변경 후보로 두었다.

계획 문서에는 변경 전후 내용, 요구사항·일정·위험·시험 영향, 결정자와 완료 증거를 기록하는 CR 양식이 준비되어 있다. 다만 실제 추가 기능 승인이나 Git 기준선 태그 생성이 완료된 것은 아니다. 결함 등록 양식 역시 준비 상태이며, 시험 통과를 모든 결함의 부재로 해석하지 않는다.

현재 확보된 관리 성과는 요구사항·작업·코드·시험·잔여 항목을 연결한 기록이다. 실제 담당자 배정, 주차별 작업 시간과 승인 자료가 없으므로 전체 진척률, 일정 준수율이나 교육 종료 실적은 산정하지 않았다. 후속 수업에서 이 자료와 LAN 검증·최종 발표 결과를 보완해야 한다.

## 3. 구현 범위와 프로그램 구조

서버는 IPv4 환경에서 연결을 순차 처리하며, 정적 파일의 GET 요청을 제공한다. `/`는 `www/index.html`로 연결하고 한글 HTML, CSS, 이미지 및 오류 페이지를 반환한다. HTTP/1.0·1.1 요청 형식을 처리하지만 연결당 첫 요청에만 응답한 뒤 `Connection: close` 정책으로 연결을 닫는다.

| 구성 요소 | 구현 역할 | 관련 파일 |
| --- | --- | --- |
| 실행·설정 | 주소·포트·문서 루트·제한값 검증, 서버 시작·종료 | __main__.py, config.py |
| 연결·수신 | 소켓 생성, 연결 수락, 헤더 누적 수신, 응답 전송 | server.py |
| 요청 해석 | 메서드·경로·버전·헤더 분석 및 비정상 입력 거부 | request.py |
| 파일 처리 | URL을 문서 루트의 파일로 연결, MIME·오류 처리 | handler.py |
| 응답 생성 | 상태 줄·헤더·본문을 바이트로 조립 | response.py |
| 기초 실습 | 받은 바이트를 그대로 돌려주는 TCP Echo 서버 | examples/tcp_echo_server.py |

HTTP 서버 모듈은 `src/mini_http/`에 위치한다. 수신, 해석, 파일 처리와 응답 생성을 분리하여 각 단계의 입력·출력을 독립적으로 시험할 수 있도록 구성하였다. Echo 실습은 HTTP 형식 해석 없이 TCP 송수신을 먼저 이해하는 별도 예제다.

기본 설정은 `127.0.0.1:8000`, 문서 루트는 `www/`, 헤더 수신 제한 시간은 5초다. 헤더 크기는 16,384바이트, 제공 파일 크기는 8,388,608바이트로 제한한다. 응답 전송에도 설정된 타임아웃을 적용한다.

## 4. 요청 수신부터 응답 종료까지

처리 흐름은 다음과 같다.

socket → bind → listen → accept → recv로 헤더 수집 → 요청 파싱 → 파일·오류 처리 → 응답 조립 → sendall → 연결 종료

**연결 준비:** 서버는 지정 주소와 포트에 소켓을 바인딩하고 연결을 기다린다. `accept()`가 반환한 연결 소켓으로 해당 클라이언트와 통신하며, 수신 대기용 소켓은 다음 연결을 받기 위해 유지한다.

**헤더 수신:** `recv()` 결과를 누적하여 헤더 종료 구분자 `\r\n\r\n`을 찾는다. 한 번의 수신이 요청 전체를 포함한다고 가정하지 않으며, 수신 중 헤더 크기와 남은 시간을 검사한다. 아무 데이터 없이 연결이 끝난 경우와 불완전한 요청을 보내고 끊어진 경우도 구분한다.

**요청 해석:** `GET / HTTP/1.1` 같은 요청 라인에서 메서드·대상·버전을 분리하고 헤더를 검증한다. HTTP/1.1의 Host 누락, 잘못된 URL·헤더, 중복 헤더와 지원하지 않는 요청 본문 등을 거부한다. GET 이외의 알려진 메서드는 해당 처리 단계에서 `405`와 `Allow: GET`, 모르는 메서드는 `501`로 응답한다.

**파일 처리:** URL의 쿼리 부분을 분리하고 경로를 디코딩·정규화한 뒤 문서 루트 내부인지 확인한다. 파일은 바이너리로 읽어 원본 바이트를 유지하고, 파일 유형에 맞는 Content-Type을 정한다. 없는 경로는 커스텀 또는 기본 `404` 페이지를 제공한다.

**응답·종료:** 상태 줄, 응답 헤더, 빈 줄, 본문을 직접 조립한다. Content-Length는 본문 바이트 수로 설정하고 `sendall()`로 전송한 뒤 연결을 닫는다. 클라이언트가 전송 중 연결을 끊는 등의 소켓 오류는 처리하여 다음 연결을 계속 받을 수 있도록 한다.

주요 오류 정책은 잘못된 요청 `400`, 접근 제한 `403`, 파일 없음 `404`, 메서드 제한 `405`, 수신 시간 초과 `408`, 헤더 과대 `431`이다. 이 밖에 Expect, 서버 I/O 오류, 미지원 기능·버전에 대한 응답도 구현되어 있다. 이는 현재 서버의 제한된 정책이며 전체 HTTP 규칙의 구현을 의미하지 않는다.

## 5. 네트워크 학습의 핵심 내용

| 학습 주제 | 코드에서 확인할 동작 | 이해할 내용 |
| --- | --- | --- |
| TCP 바이트 스트림 | 분할된 헤더를 누적하고 종료 구분자 탐색 | 송신 호출·패킷·수신 호출과 HTTP 요청의 경계는 같지 않음 |
| 프로토콜 계층 | 소켓 수신과 HTTP 파싱의 분리 | TCP 연결 성공과 올바른 HTTP 요청 처리는 서로 다른 단계 |
| 문자와 바이트 | 한글 인코딩 후 본문 길이 계산 | 문자 수 대신 실제 전송 바이트 수가 응답 길이의 기준 |
| 연결과 자원 | 요청별 연결 종료, 타임아웃과 크기 제한 | 느린 입력·과대 요청이 서버 자원과 후속 연결에 미치는 영향 |
| 주소와 포트 | 로컬 주소와 전체 인터페이스 바인딩 구분 | 서버의 수신 설정과 클라이언트의 실제 접속 주소의 관계 |
| 오류와 복구 | 오류 응답 뒤 다음 정상 요청 처리 | 잘못된 입력에 대한 응답과 서버 지속 동작을 함께 검증 |

특히 느린 클라이언트가 조금씩 데이터를 보내는 경우를 고려하여, 헤더 수신을 시작할 때 정한 전체 제한 시간에서 남은 시간을 계산한다. 단순히 매 수신마다 같은 시간을 새로 기다리는 것과 어떤 차이가 있는지 코드로 확인할 수 있다.

또한 `sendall()`의 정상 반환만으로 클라이언트 애플리케이션의 해석·표시까지 확인한 것은 아니다. 클라이언트에서 수신한 상태 코드, 헤더와 본문을 검사해야 요청·응답의 동작을 검증할 수 있다. 브라우저의 실제 화면 확인은 이와 별도의 수동 검증 항목이다.

학습 결과는 소스 작성 여부뿐 아니라 요청 경계 판단 이유, UTF-8 길이 계산, 오류 후 복구, 연결 종료 정책을 시험 결과와 함께 설명할 수 있는지로 평가한다.

## 7. 실행 및 시연 방법

서버 실행 스크립트는 어느 작업 폴더에서든 프로젝트 소스를 찾도록 구성되어 있다. 프로젝트의 Python 가상환경이 있으면 사용하고, 없으면 시스템 Python 3를 사용한다. 서버 실행에는 Python 3.10 이상이 필요하다.

```bash
# 터미널 1: 서버 시작
/home/yoondh/work/OJT_MANAGE/docs/ojt_manage_run_server
```

```bash
# 터미널 2: 헤더와 본문 확인
/home/yoondh/work/OJT_MANAGE/docs/ojt_manage_run_client

# 없는 경로의 오류 응답 확인
/home/yoondh/work/OJT_MANAGE/docs/ojt_manage_run_client http://127.0.0.1:8000/not-found
```

클라이언트 스크립트는 curl을 사용하며 요청 결과를 출력하고 종료한다. 기본 요청에서는 `200`과 HTML 본문을, 없는 경로에서는 `404`를 확인한다. 서버는 실행 터미널에서 `Ctrl+C`로 종료한다.

자동 시험은 프로젝트 루트에서 다음과 같이 실행한다.

```bash
cd /home/yoondh/work/OJT_MANAGE
.venv/bin/python3 -m pytest tests/ -q
```

권장 시연 순서는 서버 시작 → GET 정상 응답 → CSS·이미지 응답 → 없는 경로 → 자동 시험 → 서버 종료다. HTML 파일을 직접 여는 방식과 HTTP 서버에 접속하는 방식을 구분하여 시연한다. 상세 명령은 [서버 안내](./docs/ojt_manage_server_command.md)와 [클라이언트 안내](./docs/ojt_manage_client_command.md)를 참조한다.

## 8. 현재 한계와 후속 학습

현재 구현은 IPv4 순차 처리와 정적 GET에 집중한다. Keep-Alive, 동시 요청 처리, TLS, 동적 페이지, 요청 본문·업로드와 전체 HTTP 표준 지원은 구현 범위 밖이다. HEAD도 지원 메서드는 아니며, HEAD 오류 응답에서 본문을 보내지 않는 처리가 포함되어 있다.

다음 학습은 실제 다른 기기의 LAN 접속, 브라우저 시각 확인, Wireshark를 통한 연결 수립·데이터 전송·종료 관찰로 진행할 수 있다. LAN 수신에는 `--host 0.0.0.0`을 지정하고 클라이언트는 서버의 실제 LAN IP로 접속한다. 패킷 관찰 결과와 서버 로그를 비교하여 운영체제의 TCP 동작과 애플리케이션의 HTTP 처리를 연결해 이해한다.

이후 순차 처리의 대기 문제를 측정하고 동시 처리 또는 Keep-Alive를 확장 후보로 검토한다. 새로운 기능은 요구사항·위험·시험 영향을 정리한 후 추가하며, 기존 오류 처리와 자원 제한이 유지되는지 회귀시험한다.

계획 문서의 15주 일정 중 실제 주차별 성과, 팀 승인, 최종 발표·종료는 아직 완료 기록이 없다. 현재 성과는 프레임워크 없는 HTTP 서버 구현과 함께 요구사항·WBS·위험·시험·변경 기록을 연결한 것이다. 기술적으로는 바이트 송수신과 HTTP 처리를 이해하고, 관리 측면에서는 범위를 정하고 작업을 나누며 증거에 따라 완료·미완료를 판단하는 과정을 실습하였다. 실제 일정 평가와 승인·종료 기록의 보완은 이후 교육 활동으로 남아 있다.
