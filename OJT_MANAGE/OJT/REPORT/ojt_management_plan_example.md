## 1. 프로젝트 개요

본 프로젝트는 외부 회사에서 제공하는 `main()` 진입까지의 초기 구동 코드를 인수하고, 사내에서 32비트 코어의 후속 bring-up과 64비트 코어의 베어메탈·Linux bring-up을 수행한 뒤 코드와 검증 자료를 외부 회사에 인계하는 사례다.

본 사례에서는 32비트 후속 개발을 베어메탈로 가정한다. 외부 제공 코드의 64비트 적용 여부, 대상 코어·보드, 필수 주변장치와 Linux 구성은 착수 시 확정한다. Linux의 부팅 완료는 베어메탈의 `main()` 도달과 별도 기준으로 검증한다.

아래 일정과 역할은 계획 예시이며 실제 계약·완료 실적이 아니다. 코드 제공 책임과 최종 수용 책임은 구분하여 합의한다.

## 2. 개발 범위 및 완료 기준

| 개발 대상 | 주요 수행 범위 | 완료 기준 |
| --- | --- | --- |
| 32비트 후속 bring-up | 제공 코드의 main 진입 확인 후 필수 주변장치, 타이머·인터럽트, 메모리 접근 검증 | 합의한 베어메탈 시험 통과 및 재실행 로그 확보 |
| 64비트 베어메탈 | 초기 구동 기반 확인·보완, 실행 환경 및 필수 주변장치 검증 | main 진입부터 필수 시험까지 재현 가능한 코드·로그 확보 |
| 64비트 Linux | 부팅 경로, 보드 설정, 커널·루트 파일시스템 구성 및 필수 장치 확인 | 사용자 공간 셸 진입, 필수 장치 시험 및 재부팅 검증 통과 |

필수 장치 목록과 시험 방법·반복 횟수는 보드 규격을 기준으로 합의한다. 고급 성능 최적화, 저전력 모드, 전체 주변장치 지원, 양산 인증은 별도 승인 범위로 둔다. 32비트 Linux는 본 사례의 기본 범위에 포함하지 않는다.

## 3. 착수 조건 및 역할

외부 업체로부터 초기 구동 소스와 사용 조건, 빌드 도구 버전, 빌드·실행 방법, 링커 설정, 메모리 맵, 보드 버전, 정상 로그와 알려진 제약을 인수한다. 회로·레지스터 자료, 디버거, 전원 및 UART 연결 등 개발 환경도 준비한다.

인수 시험에서는 사내 환경에서 소스를 빌드하고 대상 보드의 `main()` 도달을 디버거 또는 합의한 로그로 재현한다. 실패 시 외부 제공 코드, 보드, 사내 설정 중 조사 책임을 구분하여 수정 요청한다. 인수 전에는 문서·시험을 준비하고, 후속 개발 일정은 인수 결과에 따라 확정한다.

특히 64비트 초기 구동 코드와 Linux 부팅에 필요한 기반 구성의 제공 범위·버전·책임자를 확인한다. 미제공 항목은 사내 개발 또는 외부 추가 제공으로 결정하고 일정·공수에 반영한다.

사내 PM은 범위·일정·대외 협의를, 코어 담당자는 32비트·64비트 베어메탈 개발을, Linux 담당자는 부팅·보드 지원 구성을 맡는다. 검증 담당자는 시험과 인계 재현을 확인한다. 역할은 겸임할 수 있으며 업무별 책임자 1명을 지정한다. 외부 업체는 제공 코드의 질의·결함 대응과 최종 인수 검증의 담당자를 지정한다.

## 4. 작업 분해 및 일정

개발 보드와 자료가 준비되고 외부 코드가 예정대로 제공된다는 가정하에 8주 계획을 제안한다. 병행 작업은 담당 인력과 보드가 확보된 경우에 적용하며, 실제 날짜는 착수 시 지정한다.

| 기간 | 작업 및 선행 조건 | 주요 결과 |
| --- | --- | --- |
| 1주차 | 외부 코드·환경 인수, 범위·수용 기준 합의 | 인수 시험 결과 및 계획 기준선 |
| 2~3주차 | 인수한 코드 기반 32비트 후속 bring-up | 필수 기능 코드와 시험 로그 |
| 2~4주차 | 64비트 초기 구동 기반 확보 후 베어메탈 개발 | 64비트 실행·장치 검증 결과 |
| 4~6주차 | Linux 부팅 기반 확보 후 커널·보드 구성 검증 | 셸 진입 및 필수 장치 동작 결과 |
| 7주차 | 각 대상 개발 결과의 회귀시험·패키징 | 인계 후보 버전과 미해결 목록 |
| 8주차 | 외부 업체 재현 시험, 보완 및 최종 검토 | 수용 기록과 최종 인계본 |

핵심 의존 관계는 외부 기반 코드 인수 → 대상별 개발 → 통합 검증 → 외부 수용이다. Linux 작업은 필요한 64비트 실행·메모리·부팅 조건이 확인된 범위부터 진행한다. 기반 코드 제공 지연이나 인력 부족이 발생하면 병행 범위와 인계일을 재산정한다.

주요 검토 시점은 1주차 인수·계획 확정, 4주차 중간 점검, 6주차 기능 검증, 8주차 인계 검토로 둔다.

## 5. 보고·이슈·위험 관리

주간 보고는 그룹·부문·전체 단위에서 각각 1회 수행한다. 그룹은 개발·시험, 부문은 의존 관계·자원, 전체는 일정 영향·지원 요청을 검토한다.

내부 결함·조치는 Redmine에, 외부 코드 질의·수정 요청·인계 협의는 Jira에 기록한다. 관련 번호와 코드 버전을 연결하고, 메일·회의의 주요 결정도 해당 항목에 반영한다. 외부 수정 완료 후에는 사내 검증을 거쳐 내부 이슈를 종료한다.

| 주요 위험 | 예상 영향 | 대응 계획 |
| --- | --- | --- |
| 제공 코드 지연·재현 실패 | 후속 bring-up 착수 지연 | 인수 기준 사전 합의, 담당자·수정 기한 지정, 일정 재조정 |
| 64비트·Linux 기반 누락 | 추가 개발 및 부팅 실패 | 제공 범위·호환 버전 확인, 미제공 항목의 책임·공수 확정 |
| 보드 결함·환경 차이 | 원인 분석 및 외부 재현 지연 | 보드·도구 버전 고정, 단계별 로그와 실행 절차 공유 |

진척은 main 도달, 필수 시험 통과, Linux 셸 진입, 외부 재현 등 확인 가능한 결과로 판단한다. 기한 초과 이슈와 미실행 시험을 함께 보고하고, 중대한 착수·납기 차질은 정기 보고 전에 공유한다.

범위·인계일·공수 변경은 영향 분석 후 권한자의 결정을 받아 반영한다. 최초 계획과 변경 이유를 남기고, 승인 없이 필수 장치나 완료 기준을 축소하지 않는다.

## 6. 산출물 및 외부 인계

인계본은 32비트 베어메탈, 64비트 베어메탈, 64비트 Linux를 구분하고 공통 기반 코드와 수정분의 관계를 명시한다. 소스, 설정·패치, 빌드 스크립트, 도구 버전, 실행 이미지와 검증 로그를 포함한다.

함께 제공할 문서는 빌드·실행 가이드, 보드·연결 정보, 시험 결과, 알려진 제약 및 미해결 이슈 목록이다. 커널·부트 구성·루트 파일시스템의 버전과 생성 방법도 기록하고, 재배포 가능한 범위와 필요한 사용 조건을 확인한다.

인계 후보에 버전 또는 태그를 부여한 후 외부 업체가 합의한 환경에서 빌드·실행·필수 시험을 재현한다. 차이는 Jira에서 추적하고 수정 후 재검증한다. 파일 전달과 기술 설명만으로 수용 완료로 간주하지 않으며 외부 확인자의 결과를 기록한다.

## 7. 종료 판단 및 기대 효과

세 개발 대상의 필수 시험, 인계본 재현, 외부 수용 기록을 모두 확인한 후 종료한다. 부팅 불가나 필수 기능 실패는 해결 후 인계하며, 남은 경미한 항목은 영향·담당·기한과 인수 동의를 명시한다. 인계 후 지원 기간과 대응 범위도 합의한다.

성과는 계획 대비 일정, 필수 시험 결과, 외부 재현 여부로 평가한다.
