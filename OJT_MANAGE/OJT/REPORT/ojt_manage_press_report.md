## 1. 통제 목적 및 적용 범위

본 사례는 외부 회사의 `main()` 진입 코드를 인수한 뒤, 사내에서 32비트 후속 bring-up과 64비트 베어메탈·Linux bring-up을 수행하여 외부에 인계하는 프로젝트를 대상으로 한다. 32비트는 베어메탈이며, 외부 업체가 두 코어의 초기 코드와 Linux 참조 부팅 구성을 제공한 설정을 유지하였다.

통제의 목적은 계획과 실제 상태의 차이를 조기에 확인하고, 원인·영향 분석을 거쳐 조정한 뒤 결과를 검증하는 것이다. 특히 Linux 장치 검증이 6주차에서 7주차로 지연된 상황에서 필수 품질 기준과 8주차 인계 목표를 함께 관리한 과정을 다룬다.

기본 흐름은 기준 확인 → 차이 감지 → 원인·영향 분석 → 대안 결정 → 조치 실행 → 효과 확인이다. 조치 후에도 문제가 남으면 다시 검토하고, 기준선 변경이 필요하면 권한자의 결정을 받아 반영한다.

## 2. 기준선과 통제 기준

착수 시 합의한 개발 범위, 일정, 필수 시험과 인수 조건을 비교 기준으로 설정하였다. 원래 기준은 보존하고 최신 예상 일정 및 승인된 변경을 별도로 기록하였다.

| 통제 대상 | 사례의 기준 | 조정·보고가 필요한 조건 |
| --- | --- | --- |
| 범위 | 32비트 베어메탈, 64비트 베어메탈·Linux 및 합의한 필수 기능 | 장치 추가, 성능 목표 추가 또는 필수 시험 축소 요청 |
| 일정 | Linux 기능 검증 6주차, 회귀시험 7주차, 외부 인계 8주차 | 단계 완료 지연 또는 후속 시험·인계 일정 영향 예상 |
| 품질 | 대상별 필수 시험과 최종 인계본 재현 | 필수 기능 실패, 재검증 누락, 부팅 성공만으로 완료 판단 |
| 형상 | 코드·설정·도구·보드 버전과 시험 대상의 대응 | 검증 버전과 인계 버전의 불일치 |
| 자원·비용 | 합의한 담당 역할과 가용 장비·승인 자원 범위 | 담당자·보드 충돌, 추가 투입 또는 구매 필요 |
| 외부 인수 | 외부 업체의 빌드·실행·필수 시험 재현 및 수용 확인 | 회신 지연, 실행 안내 누락, 외부 환경의 재현 실패 |

진척은 main 도달, 필수 장치 시험, Linux 셸 진입, 회귀시험, 외부 수용처럼 증거로 확인 가능한 상태로 관리하였다. 예산과 실제 공수 자료가 없는 사례이므로 비용 준수율이나 절감액은 산정하지 않았다.

## 3. 점검·보고 및 의사결정 체계

그룹·부문·전체 단위에서 각각 주 1회 보고하는 체계를 적용하였다. 그룹은 담당별 진행과 결함을 확인하고, 부문은 일정 의존 관계와 검증 자원을 조정하며, 전체는 인계일 영향과 권한 밖의 지원·변경 사항을 검토하였다. 인계 차질이 예상되는 문제는 정기 보고를 기다리지 않고 수시 공유하였다.

PM은 기준 대비 차이, 예상 완료일과 결정 요청을 취합하였다. 개발 담당자는 원인·조치를, 검증 담당자는 시험 범위와 통과 증거를 책임졌다. 부문 책임자는 위임된 범위의 작업 순서를 조정하고, 최종 인계일·계약 범위·추가 비용은 해당 권한자가 결정하도록 구분하였다.

내부 조치는 Redmine, 외부 질의·수정·인계 협의는 Jira에 기록하였다. 보고에는 관리번호·코드 버전·현황 기준 시각을 남겼다. 결정 기록은 안건, 영향, 선택안, 결정자·근거, 담당자·기한, 확인 결과로 구성하고 다음 보고에서 이행 여부를 점검하였다.

## 4. 일정 지연 통제 사례

6주차에 Linux 셸 진입은 확인되었으나 필수 장치 시험이 실패하여 계획한 기능 검증을 완료하지 못했다. 실제 보드와 장치 설정의 차이를 조사 대상으로 좁히고, 수정뿐 아니라 장치 재시험·재부팅·회귀시험에 필요한 시간을 포함해 후속 영향을 검토하였다.

검토 시점에는 Linux 완료 예상이 7주차로 바뀌어 통합 검증과 인계 준비가 겹쳤다. PM은 아래 대안을 부문 검토에 제시한 것으로 구성하였다.

| 검토 대안 | 일정·품질 영향 | 사례의 판단 |
| --- | --- | --- |
| 전체 후속 작업 순연 | 재검증 시간을 확보하지만 8주차 인계 변경 가능 | 7주차 검증 미완료 시 적용할 대안으로 유지 |
| 독립 작업 병행 | 공통 문서·베어메탈 인계 준비를 먼저 수행하고 Linux는 수정 후 검증 | 가용 담당자·장비 확인 후 선택 |
| 필수 시험 일부 생략 | 단기 일정은 줄지만 합의한 수용 기준 미충족 | 채택하지 않음 |

부문 책임자는 필수 시험을 유지하면서 독립 작업을 병행하는 조치를 결정한 것으로 설정하였다. Linux 담당자는 수정본과 영향 범위를 제시하고, 검증 담당자는 7주차 내 관련 시험을 수행하며, 인계 담당자는 이미 확정된 자료를 먼저 정리하도록 책임을 나누었다.

Linux 수정·검증 상태는 해소 시까지 일별로 확인하였다. 최초 6주차 계획을 덮어쓰지 않고 최신 예상일과 조정 이유를 기록했으며, 외부에는 8주차 인계 목표와 잔여 검증 조건을 공유하였다. 7주차 검증을 마치지 못하면 인계일 변경 협의를 진행하도록 재판단 기준을 두었다.

사례상 7주차 장치·재부팅 및 관련 회귀시험을 완료하고 8주차 인계를 유지하였다. 이는 최종 인계일을 지킨 결과이며, Linux 중간 일정의 1주 지연은 일정 차이로 남겼다.

## 5. 품질·형상 및 외부 협업 통제

**초기 코드 인수:** 1주차 빌드 재현 실패에 대해 외부 도구 버전·옵션을 Jira로 확인하였다. 사내 환경과 빌드 스크립트를 맞춘 뒤 각 코어의 main 도달을 확인하여 인수하였다. 파일 수령만으로 인수 완료 처리하지 않았다.

**결함 검증:** 32비트 타이머 인터럽트 문제는 초기화 순서 수정 후 해당 시험과 연관 기능을 다시 확인하였다. Linux는 셸 진입, 장치 동작과 재부팅을 구분하고, 장치 시험이 실패한 동안에는 전체 기능을 미완료로 표시하였다. 외부 답변이나 개발자의 수정 완료만으로 내부 결함을 종료하지 않았다.

**형상 일치:** 외부 제공 원본과 사내 수정분을 구분하고, 코드·도구·보드·실행 이미지 버전을 시험 기록에 연결하였다. 최종 수정이 들어간 경우 기존 로그를 그대로 수용 증거로 쓰지 않고 영향 범위에 따라 재검증하였다. 인계 후보를 고정한 뒤 변경이 발생하면 후보 버전과 해당 시험 결과를 함께 갱신하였다.

**외부 수용:** 8주차 외부 재현에서 실행 순서 안내가 부족한 문제가 확인되어 가이드를 보완한 것으로 설정하였다. 외부 담당자가 인계본으로 다시 빌드·실행·필수 시험을 확인한 후 수용 의견을 남기도록 관리하였다. 내부 기록에는 외부 결과와 사내 종료 판단을 연결하였다.

## 6. 범위·변경 및 자원 통제

Linux 보드 설정 수정은 합의된 기능을 복구하는 결함 수정으로 분류하였다. 필수 기능·완료 기준은 유지하면서 작업 순서와 예상 일정을 조정하였다. 추가 주변장치, 고급 성능 최적화, 저전력 및 양산 인증은 기본 범위 밖에 두고 이번 인계에 포함하지 않았다.

범위·최종 인계일·비용을 바꾸는 요청은 변경 전후 내용, 사유, 영향을 받는 작업·시험·공수와 대안을 기록한 후 권한자에게 판단을 요청하는 기준을 적용하였다. 승인된 경우에만 계획과 외부 합의 내용을 갱신하며, 단순한 진행 상태 변경과 기준선 변경을 구분하였다.

독립 작업 병행은 담당자와 장비를 동시에 사용할 수 있는지 확인한 후 결정하였다. 같은 검증 담당자나 보드에 작업을 중복 배정하지 않고, 자원 충돌이 발생하면 우선순위 또는 완료 예상일을 다시 조정하도록 하였다. 추가 인력·구매가 있었다는 실적이나 비용 효과는 본 사례에서 가정하지 않았다.

## 7. 통제 결과 및 개선사항

| 통제 항목 | 사례상 결과 | 확인 근거로 관리할 기록 |
| --- | --- | --- |
| 일정 | Linux 중간 완료 1주 지연, 최종 인계 8주차 유지 | 최초 계획, 예상·완료 시점, 일정 조정 결정 |
| 품질 | 필수 시험을 유지하고 수정 후 회귀시험 완료 | 대상 버전별 시험 결과와 결함 재검증 기록 |
| 범위·형상 | 기본 범위 유지, 검증·인계 대상 버전 일치 확인 | 범위 목록, 변경 이력, 인계 구성 목록 |
| 외부 인수 | 가이드 보완 후 외부 재현·수용 확인 | Jira 협의, 재현 결과, 수용 의견 |

본 사례의 통제 효과는 지연 사실을 숨기지 않고 작업 간 의존 관계를 조정하면서 품질 조건을 유지한 데 있다. 최종 인계일 준수만으로 계획 전체가 준수되었다고 평가하지 않으며, 비용 성과는 자료가 확보된 이후 판단한다.

다음 프로젝트에서는 인수 체크리스트에 도구·보드 대응 정보를 포함하고, Linux 장치 검증과 외부 재현의 여유 기간을 계획에 반영한다. 또한 이슈별 다음 확인일과 재판단 조건을 정하여 조치가 장기 대기로 남지 않도록 한다. 종료 시에는 필수 결함·미실행 시험·미결 결정의 잔여 여부와 외부 수용 기록을 최종 확인한다.
