## 1. 수행 개요

외부 회사가 제공한 `main()` 진입까지의 초기 구동 코드를 인수한 후, 사내에서 32비트 후속 bring-up과 64비트 베어메탈·Linux bring-up을 수행하고 결과를 외부 회사에 인계한 사례로 구성하였다.

착수 시 32비트 후속 개발은 베어메탈로 확정하고, 외부 업체가 두 코어의 초기 구동 코드와 64비트 Linux용 참조 부팅 구성을 제공한 것으로 가정하였다. 사내는 이후 필수 기능 구현·보드 설정·검증을 맡고, 외부는 제공 코드의 결함 대응과 최종 재현·수용을 맡았다.

전체 기간은 계획과 같은 8주로 설정하였다. Linux 필수 장치 검증은 보드 설정 문제로 1주 지연되었으나, 준비 가능한 문서·패키징을 병행하고 7주차 회귀시험 후 8주차 인계를 마친 흐름이다. 필수 시험 범위와 수용 기준은 유지하였다.

## 2. 외부 코드 인수 및 환경 구축

1주차에는 외부 업체로부터 초기 구동 소스, 빌드·실행 방법, 도구 버전, 링커 설정, 메모리 맵과 정상 로그를 인수하였다. 사내 담당자는 보드 버전, 디버거 및 UART 연결을 확인하고 동일한 조건에서 빌드·실행을 재현하였다.

최초 재현 과정에서는 사내 도구 버전이 제공 환경과 달라 빌드 문제가 발생한 것으로 설정하였다. Jira로 권장 도구와 옵션을 확인하고 빌드 스크립트에 반영한 뒤, 각 대상 보드의 `main()` 도달을 확인하여 초기 코드 인수를 마쳤다.

인수한 코드는 기준 버전으로 보존하고 사내 수정분을 구분하였다. 코어·보드·도구·실행 이미지의 대응 관계를 기록하여 이후 문제가 코드 변경인지 환경 차이인지 비교할 수 있도록 하였다.

## 3. 대상별 개발 및 검증 결과

필수 기능은 UART 송수신, 타이머·인터럽트, 지정 메모리 영역 접근으로 정한 사례다. Linux는 셸 진입과 합의한 장치 동작·재부팅을 별도로 확인하였다. 결과는 아래와 같이 구성하였다.

| 개발 대상 | 수행 내용 | 사례상 검증 결과 |
| --- | --- | --- |
| 32비트 후속 bring-up | main 이후 UART·타이머·인터럽트 처리 및 메모리 접근 시험 | 초기화 순서 보완 후 필수 시험 통과 |
| 64비트 베어메탈 | 제공 초기 코드 기반 실행 환경·필수 장치 검증 | main 진입부터 장치 시험까지 재실행 확인 |
| 64비트 Linux | 참조 부팅 구성 적용, 커널·보드 설정·루트 파일시스템 구성 | 장치 설정 수정 후 셸·필수 장치·재부팅 시험 통과 |

32비트 개발은 외부 제공 코드 이후의 기능을 중심으로 진행하였다. 타이머 인터럽트의 초기화 순서 문제를 수정하고 관련 기능을 다시 시험하였다. 64비트 베어메탈은 32비트 시험 항목을 참고하되 대상 코어의 실행 조건과 설정에 맞춰 별도로 구현·검증하였다.

Linux는 베어메탈의 `main()` 도달을 완료 근거로 사용하지 않았다. 커널 기동, 사용자 공간 셸 진입, 장치 동작과 재부팅을 순서대로 확인하고 각 단계의 로그를 구분하였다. 시험하지 않은 주변장치, 성능 최적화, 저전력 및 양산 인증은 완료 범위에서 제외하였다.

## 4. 계획 대비 수행 경과

| 주요 작업 | 계획 | 사례상 수행 결과 |
| --- | --- | --- |
| 외부 코드·환경 인수 | 1주차 | 도구 설정 보완 후 1주차 완료 |
| 32비트 후속 개발 | 2~3주차 | 인터럽트 관련 수정·재검증 후 3주차 완료 |
| 64비트 베어메탈 | 2~4주차 | 4주차 필수 시험 완료 |
| 64비트 Linux | 4~6주차 | 셸 진입 후 장치 검증 지연, 7주차 완료 |
| 회귀시험·패키징 | 7주차 | 준비 가능한 자료를 먼저 정리하고 최종 수정 후 회귀시험 완료 |
| 외부 재현·인계 | 8주차 | 실행 안내 보완 후 재현 및 수용 확인 |

6주차에는 Linux 지연 원인과 인계 영향을 부문 보고에 올리고 검증 순서를 조정하였다. 베어메탈 결과와 공통 문서는 먼저 정리하되, Linux 최종본이 확정되기 전에는 전체 검증 완료로 보고하지 않았다.

7주차 수정 후 Linux 장치 시험과 관련 회귀시험을 완료하여 최종 인계일을 유지한 것으로 구성하였다. 재검증이 끝나지 않았다면 필수 시험을 생략하지 않고 인계일 변경을 요청하는 기준을 적용하였다.

## 5. 주요 이슈 및 조치 사례

| 가상 이슈 | 조사 및 조치 | 확인 결과 |
| --- | --- | --- |
| 외부 코드 빌드 재현 실패 | 외부 업체와 도구 버전·옵션 차이를 확인하고 실행 환경 고정 | 깨끗한 작업 환경에서 재빌드·main 도달 확인 |
| 32비트 타이머 인터럽트 미발생 | 관련 초기화 순서를 점검하고 사내 코드를 수정 | 인터럽트 발생·처리 및 연관 기능 재검증 |
| Linux 셸 진입 후 필수 장치 미동작 | 실제 보드와 장치 설정의 차이를 확인하고 외부 자료와 대조·수정 | 해당 장치 시험과 재부팅 후 동작 재확인 |

각 이슈는 재현 조건, 사용 버전, 영향, 담당자, 조치 기한과 시험 결과를 Redmine에 기록한 것으로 설정하였다. 외부 확인이 필요한 항목은 Jira와 연결하고, 외부 답변을 받은 뒤에도 사내 재현·검증을 수행한 후 종료하였다.

Linux 설정 변경은 원래 합의한 필수 기능을 복구하는 결함 수정으로 처리하였다. 일정 조정의 영향과 결정은 별도로 기록하고, 새로운 주변장치 추가나 성능 개선은 이번 인계에 포함하지 않았다.

## 6. 업무보고 및 협업 운영

주간 보고는 그룹·부문·전체 단위에서 각각 1회 수행하는 운영 방식을 적용하였다. 그룹 보고에서는 코드 변경과 시험 상태를, 부문 보고에서는 베어메탈·Linux 간 의존 관계와 검증 자원을, 전체 보고에서는 인계 일정과 주요 지원 사항을 검토하였다.

보고에는 금주 결과, 차주 계획, 미해결 이슈, 결정 요청과 이전 조치 결과를 포함하였다. 진척은 작업량의 임의 비율 대신 main 도달, 필수 시험, Linux 장치 검증, 외부 재현 같은 확인 가능한 결과로 설명하였다.

내부 진행·결함 기록은 Redmine, 외부 코드 질의·수정 협의·인계는 Jira로 관리하였다. 메일이나 회의에서 결정된 사항도 관련 항목에 옮기고, 보고 자료에는 관리번호와 해당 코드 버전을 연결하였다.

## 7. 산출물 인계 및 종료

최종 산출물은 32비트 베어메탈, 64비트 베어메탈, 64비트 Linux로 구분하였다. 각 묶음에 소스·설정·패치, 빌드 스크립트, 도구 버전, 실행 이미지와 시험 자료를 포함하고 외부 제공 원본과 사내 수정분을 구별하였다.

빌드·실행 가이드에는 보드 연결, 커널·부트 구성·루트 파일시스템의 버전과 생성 방법, 정상 동작 확인 절차를 정리하였다. 알려진 제약과 지원 범위도 함께 전달한 것으로 설정하였다.

8주차 외부 재현에서는 이미지 실행 순서에 대한 안내가 부족하여 가이드를 보완한 사례를 포함하였다. 이후 외부 담당자가 인계본을 빌드·실행하고 필수 시험을 재현하여 수용 의견을 남긴 것으로 구성하였다. 파일 전달과 외부 재현·수용은 구분하여 관리하였다.

사례상 종료 조건은 세 대상의 필수 시험 통과, 인계본 재현, 외부 수용 및 미해결 필수 결함 없음이다. 실제 종료 보고에는 코드 버전, 시험 로그, 수용 기록과 지원 기간을 연결해야 한다.

## 8. 수행 평가 및 개선사항

외부 코드의 빌드 재현과 책임 범위를 착수 시 확인하는 것이 후속 개발의 기준을 세우는 데 도움이 되었다. 또한 Linux의 셸 진입과 장치 검증을 분리하여 부팅 성공만으로 개발 완료를 판단하는 일을 방지하였다.

개선사항은 외부 인수 체크리스트에 도구·옵션과 보드 대응 정보를 포함하고, Linux 필수 장치 시험을 조기에 준비하며, 최종 인계 전에 별도 작업 환경에서 가이드를 따라 재현하는 것이다. 이 사례에서는 전체 8주 일정을 유지했지만 Linux 중간 일정은 지연되었으므로, 다음 계획에는 장치 검증과 외부 재현의 여유 기간을 명시하는 것이 필요하다.
